# Woo Markdown Vault 文件化存储方案

状态：待评审

## 1. 结论

该需求真实、可行，并且与 Woo 的“本地优先”定位一致。

推荐把 Markdown 文件设为文稿内容的唯一事实源：新建文稿时立即创建 `.md` 文件，编辑时直接原子写回该文件。SQLite 不再保存当前正文，只保存索引、排序、同步状态、版本历史和其他派生数据。

不推荐长期采用“SQLite 正文 + Markdown 镜像”方案。两个可写副本无法稳定判断谁是最新版本，应用崩溃、外部编辑、云同步和重命名都可能产生静默覆盖。

## 2. 目标

- 桌面端每一份正式文稿都有一个用户可见、可直接使用其他编辑器打开的 `.md` 文件。
- 新建、重命名、移动和删除文稿分别对应文件系统的创建、重命名、移动和删除。
- Woo 关闭时，用户对文件的外部修改在下次启动后仍能被识别。
- 保留现有目录、版本历史、回收站和 Supabase 同步能力。
- 迁移失败时不影响现有数据库文稿。

## 3. 非目标与边界

- 不保证 Markdown 字节级无损往返。Tiptap 在 `Markdown -> HTML -> Markdown` 后可能调整空行、列表符号和表格对齐格式，但语义应保持一致。
- Markdown 无法原生表达的格式使用兼容 HTML，例如 `<u>`、`<mark>`。
- 明文 `.md` 与“文件内容保密”不可同时满足。加锁语义必须单独决策。
- iOS/Android 不能像桌面端一样长期自由访问任意用户目录；移动端只能先使用应用私有目录，Android 后续可接入 SAF。

## 4. 推荐存储结构

用户首次开启文件库模式时选择一个 Vault 根目录：

```text
Woo Notes/
├── 工作/
│   ├── 项目计划.md
│   └── 周报.md
├── 生活/
│   └── 旅行清单.md
├── _assets/
│   └── <document-id>/
│       └── image-001.png
└── .woo/
    ├── manifest.json
    ├── trash/
    └── recovery/
```

约定：

- 应用目录映射为真实目录。
- 文稿标题默认映射为文件名，并处理非法字符和重名。
- 本地图片复制到 `_assets/<document-id>/`，Markdown 中使用相对路径。
- `.woo/manifest.json` 只保存稳定 ID 与相对路径等元数据，不保存正文。
- 当前 SQLite 继续位于应用数据目录，作为索引和状态库，而不是正文源。

建议的 manifest 条目：

```json
{
  "id": "document-uuid",
  "path": "工作/项目计划.md",
  "contentHash": "sha256:...",
  "updatedAt": "2026-08-07T12:00:00Z"
}
```

不默认向 Markdown 注入 Woo 专用 front matter。单独复制一个 `.md` 文件时，它仍是完全独立的普通文档；重新导入 Woo 时可分配新 ID。

## 5. 数据职责

| 数据 | 唯一事实源 | SQLite 中的角色 |
| --- | --- | --- |
| 当前正文 | `.md` 文件 | 不保存，或仅保留可丢弃的解析缓存 |
| 文件路径 | manifest + 文件系统 | 快速查询缓存 |
| 目录层级 | 文件系统目录 | 排序与 UI 状态 |
| 文稿 ID | manifest | 主键和同步映射 |
| 版本历史 | SQLite | Markdown 历史快照 |
| 搜索索引 | `.md` 派生 | 可重建 FTS 索引 |
| 同步游标/墓碑 | SQLite | 保持现有职责 |

任何时候发生不一致，以磁盘 `.md` 内容为准；索引可以重建。

## 6. 核心流程

### 6.1 新建

1. 根据当前目录生成目标路径。
2. 处理文件名非法字符和重名，例如 `未命名文稿 2.md`。
3. 先写临时文件，再原子重命名为目标文件。
4. 文件创建成功后写 manifest 和 SQLite 元数据。
5. 任一步失败则不在 UI 中留下虚假文稿。

建议在 Vault 模式下取消“第一行持续自动改文件名”。文稿名由明确的重命名操作控制，否则编辑第一行会频繁移动文件并破坏外部链接。首次输入标题后是否自动命名，可作为一次性行为单独评审。

### 6.2 编辑保存

```text
Tiptap HTML
    -> editorHtmlToMarkdown()
    -> 写入同目录临时文件
    -> fsync
    -> 原子替换目标 .md
    -> 记录 SHA-256
    -> 更新 manifest / SQLite 索引
```

- 沿用当前 800ms 防抖。
- 只有文件原子替换成功后才显示“已保存”。
- `.woo/recovery/` 保存崩溃恢复内容，成功落盘后清理。

### 6.3 外部修改

Rust 端使用成熟的 `notify` 文件监听库，建议 250ms 合并连续事件。

- 新增 `.md`：导入为新文稿。
- 修改 `.md`：校验哈希后刷新编辑器。
- 移动或重命名：更新 manifest 与 SQLite 路径。
- 删除：从列表移除并保留版本记录；不重新创建用户主动删除的文件。
- Woo 自己产生的写入通过“路径 + 写入后哈希”抑制回声事件。

当外部修改到达且编辑器仍有未落盘内容时：

1. 把编辑器内容保存为 `原文件名 (Woo 冲突 时间).md`。
2. 主文稿加载磁盘版本。
3. 两个文件都进入文稿列表，绝不静默覆盖。

### 6.4 重命名与移动

- 文稿重命名使用同文件系统内的原子 rename。
- 跨磁盘移动使用“复制、校验哈希、删除源文件”。
- 重名追加数字，不覆盖已有文件。
- 目录重命名后批量更新 manifest 中的相对路径。

### 6.5 删除与回收站

- 应用内删除：移动到 `.woo/trash/<document-id>/原文件名.md`，对应 `deleted = 1`。
- 恢复：优先恢复原路径；路径被占用时追加数字。
- 清空回收站：沿用现有 `deleted = 2` 和清理窗口，最后删除物理文件与版本。
- 用户在系统文件管理器中直接删除文件：视为外部删除，不私自恢复。

## 7. 图片和表格

### 图片

- Vault 模式下，本地图片不写入 base64，而是复制到 `_assets/<document-id>/`。
- 文件名冲突时追加数字，写入相对 Markdown 链接。
- 远程图片 URL 原样保存。
- 迁移现有 base64 图片时，提取为独立图片文件并改写链接。

### 表格

- 使用 GFM pipe table 作为落盘格式。
- 合并单元格、单元格颜色等 GFM 不支持的能力暂不提供，避免写出只能由 Woo 识别的私有格式。

## 8. SQLite 与数据模型调整

建议新增或调整字段：

```text
note_document
- id
- folder_id
- title
- file_path          相对 Vault 路径
- content_hash       最近成功落盘的 Markdown SHA-256
- file_mtime
- content_format     html | markdown，迁移期使用
- 其他现有状态字段
```

`content` 字段分阶段退出：

1. 迁移期保留旧 HTML，只读回滚使用。
2. Vault 稳定后不再更新当前正文。
3. 至少经过一个稳定版本后再执行删除字段迁移。

版本表的 `content` 改为保存 Markdown 快照，并写入 `content_format = markdown`。

## 9. 云同步调整

Supabase 中的文稿正文应逐步切换为 Markdown，并增加 `content_format`：

- 旧记录默认为 `html`，拉取时转换一次。
- 新客户端上传 `markdown`。
- 拉取成功后先原子写文件，再更新同步游标。
- 推送读取磁盘文件，而不是读取编辑器或 SQLite 缓存。
- 删除仍通过现有墓碑传播。
- 同时修改不继续使用简单 LWW 覆盖；保留主文件并生成物理冲突副本。

移动端使用应用私有 Vault：同步得到的 Markdown 同样真实落盘，但普通用户不能直接通过系统文件管理器访问。Android SAF 和 iOS 文件提供器可在后续阶段补齐。

## 10. 加锁文稿的产品决策

这是方案实施前必须确认的边界：

| 方案 | 可直接拿到 `.md` | 内容保密 | 推荐场景 |
| --- | --- | --- | --- |
| UI 锁 | 是 | 否 | 防止应用内误看 |
| 加密文件 `.woo` | 否 | 是 | 真正敏感内容 |
| 加密目录由系统提供 | 解锁后是 | 是 | FileVault/BitLocker 等系统能力 |

推荐：Woo 的“加锁”在 Vault 模式下明确改名为“应用内隐藏”，不宣称加密；真正保密交给系统磁盘加密。若必须支持应用级加密，则加锁文稿是“每份文稿都有可直接读取 `.md`”规则的明确例外。

## 11. 迁移方案

### 阶段 A：能力落地，不切默认

- 新增 Vault 设置、文件 API、manifest 和 watcher。
- 保持现有数据库模式为默认。
- 外部 `.md` 从“草稿映射”升级为一等文稿。

### 阶段 B：可回滚迁移

1. 用户选择 Vault 目录。
2. 预检目录权限、剩余空间、文件名冲突。
3. 将全部现有正文转换到临时迁移目录。
4. 校验文稿数量、文件可解析性和 SHA-256。
5. 原子移动到目标路径并写 manifest。
6. 全部成功后才把账户切换为 Vault 模式。
7. 原数据库正文保留一个稳定版本周期，只读用于回滚。

迁移不自动删除任何原数据库数据或用户已有文件。

### 阶段 C：切换默认与清理

- 新用户默认启用 Vault。
- 完成云端 `content_format` 迁移。
- 稳定后再移除 SQLite 当前正文。

## 12. 验收标准

- 点击新建后，目标目录立即出现 `.md` 文件。
- 编辑停止 800ms 后，外部编辑器能读到最新内容。
- 强制结束 Woo 不会留下半个文件或零字节文件。
- Woo 关闭期间修改、移动、新增或删除文件，重开后状态正确。
- 外部修改与未保存编辑并发时生成冲突副本，不丢任一版本。
- 目录和文稿重命名不覆盖已有文件。
- 图片使用可移植的相对路径，整个 Vault 拷贝后仍能显示。
- 迁移前后文稿数量一致，Markdown 均可被常见编辑器打开。
- 云同步和墓碑不会把较新的本地文件静默覆盖。

## 12.1 移动端编辑一致性

- Android/iOS 编辑页也必须支持正文格式、图片插入、表格插入和表格行列编辑。
- 移动端没有桌面右键菜单，使用触控工具栏和底部弹层完成相同命令；长按不依赖系统英文菜单。
- 有实体键盘时，移动端使用与桌面端相同的快捷键配置、冲突检测和默认组合键。
- 两端都以 Tiptap HTML 作为编辑期间的中间模型，保存时写入同一 `note_document.content`，不改变现有同步协议。
- 本地图片在当前数据库模式下暂以 data URL 保存；Vault 模式落地后统一改为 `_assets/<document-id>/` 相对路径。

## 13. 本次评审需要确认

1. Vault 是桌面端默认模式，还是先作为可选模式灰度一个版本？建议先可选。
2. 文稿名是否只通过明确重命名控制？建议是，取消第一行持续自动改文件名。
3. 加锁是否接受降级为应用内隐藏？建议接受，并把真正保密交给系统磁盘加密。
4. 移动端是否接受先使用应用私有 Vault？建议接受，后续再做 Android SAF/iOS 文件提供器。
5. 是否接受语义等价而非 Markdown 字节级无损？这是继续使用 Tiptap 所必需的约束。
